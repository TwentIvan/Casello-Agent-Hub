# Token personali su /api — piano di implementazione

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** i token personali `cas_…` valgono anche su `/api`, con ambiti `mcp`, `api:read`, `api:write` e operazioni riservate al login.

**Architecture:** colonna `api_tokens.scopes`; `lib/api-tokens.ts` crea, elenca e autentica con gli ambiti; `requireAuth` in `lib/auth.ts` sceglie token o sessione e controlla l'ambito per metodo; middleware `sessionOnly` sulle route riservate; console nella pagina Account.

**Tech Stack:** Express 5, Drizzle/Postgres (PGlite nei test), Vitest, OpenAPI + Orval, React.

**Spec:** `docs/superpowers/specs/2026-10-31-casello-token-api-design.md`

## Global Constraints

- Italiano per commenti, messaggi d'errore e commit (`feat(casello): …`); identificatori in inglese. Contract-first: OpenAPI poi codegen (generati committati); `parseRequest` / `*Response.parse`.
- Migrazione additiva e idempotente: `docs/migrations/2026-10-token-api.sql` + `docs/schema-casello.sql` + fixture `test/fixtures/schema-pre-token-api.sql` + test.
- Ambiti: `mcp`, `api:read`, `api:write`; `api:write` include la lettura; default `["mcp"]`; almeno uno, senza ripetizioni.
- Messaggi fissi: 401 «token non valido o scaduto»; 403 «il token non ha l'ambito per questa operazione»; 403 «operazione disponibile solo con il login»; senza header e senza sessione resta 401 «Login richiesto».
- GET e HEAD → `api:read` o `api:write`; POST, PUT, PATCH, DELETE → `api:write`.
- Con l'header `Authorization` presente si usa solo il token (anche con `AUTH_DISABLED=true` e anche con un cookie valido).
- Limite: 120 richieste al minuto per token su `/api` (chiave: id del token) → 429.
- Mai nei log l'header `Authorization`, il token o il suo hash.
- `pnpm run typecheck` verde prima di ogni commit.

## Review Focus

1. Token `api:write` su una route di gestione account non marcata `sessionOnly` (es. una route nuova in `ai.ts`): l'elenco delle route riservate deve essere verificato da un test che le prova tutte → test «ogni route sessionOnly risponde 403» in Task 2.
2. Header `Authorization` presente ma con schema diverso da Bearer, o Bearer con un valore che non inizia per `cas_`, con un cookie valido nella stessa richiesta: 401, mai la sessione → test in Task 2.
3. Token revocato mentre uno script lo usa: la richiesta successiva risponde 401 subito (nessuna cache) → test in Task 2.
4. Token creato con solo `api:read` usato su `/mcp`: 401 → test in Task 1.
5. Utente rimosso da `ALLOWED_EMAILS`: il token smette di valere su `/api` come su `/mcp` → test in Task 2.
